# v1.6.1 registered-appearance display audit

Date: 2026-09-10. Baseline: v1.5.7 (`eb51b3d`) -> v1.6.0 (`0836ccb`).

## Evidence and scope

A user reported wigs/clothing not appearing after upgrading to 1.6.0 and
rolling back to 1.5.7. No reporter log, runtime, backend, mod list, affected
actor, asset, or distinction between catalog absence and model absence is
available. The maintainer's local game logs are **not** evidence for this
report. Successful recovery after rollback was not separately confirmed in
the original wording. Do not assume SE 1.5.97, DAVE, or IED.

## Confirmed regression: attachment disabled by unknown visitor ownership

In 1.5.7, a valid pre-patched custom-skin CALL was chained and the additional
SFS armor pass was installed. In 1.6.0, `ConfigureIedCustomSkinCompatibility`
returned false for every pre-patched target not proven to belong to IED.
Both `InstallCustomSkinHookSE` and `InstallCustomSkinHookAE` then returned
before installing the stub that calls `ApplyAdditionalDisplayArmors`.

The menu, saved registrations, worn-mask changes and real-equipment hiding
could remain active while the sole additional-armor attachment pass never ran.
This affects any registered ARMO using that pass, including wigs and clothing,
and is independent of Native/DAV/DAVE selection. It requires a valid existing
CALL chain with unrecognized ownership; it does not occur on an untouched
engine CALL merely because the game is SE or AE.

Fix: keep the attachment hook for a verified CALL instruction. A transparent
chain ending at the exact engine visitor retains SFS filtering. A verified IED
chain retains the original-engine filter and deferred actor-level IED refresh.
An opaque foreign target receives the **original concrete game visitor**;
its engine callbacks now filter hidden actual equipment in a scoped context,
and the additional SFS attachment still follows. Invalid opcodes and unverified
jump/resume layouts continue to be rejected.

### Follow-up: opaque-chain actual-equipment filtering

The initial 1.6.1 candidate retained the original visitor but could not filter
its callbacks. That limitation is now corrected without substituting an SFS
object. At installation, patch only slots 1/2/3 of the versioned engine
`VTABLE___InitWornVisitor` (SE 241890 / AE 195851); these are the flat
`IItemChangeVisitor::Visit`, `ShouldVisit`, and `Unk_03` callbacks declared in
the pinned CommonLib source. Preserve the concrete object's address, vptr,
RTTI, destructor and fields, and chain the previously installed callbacks.
Use one expected-bytes-verified write; a rejected write is logged and does not
disable the additional attachment pass. Install only for an opaque CALL chain
after the supported runtime layout was resolved, before gameplay begins.

A stack-only thread-local scope matches the exact visitor pointer and shares
the dispatch's DisplaySet/ShouldHideRealArmor policy. Visible/protected/forced
visible/registered armor exclusions therefore follow the existing policy.
No inventory, ExtraData, equipment flags, shared ARMO records, morph ownership,
or persistent actor cache is edited. Scopes shadow by visitor identity and
restore in LIFO order, including C++ exception unwind. Unrelated visits chain
unchanged even though they share the engine vtable. Inactive and nested known
routes explicitly shadow outer filtering for the same visitor.

This fixes the missing filter for opaque chains using the original engine
visitor interface. It cannot guarantee arbitrary foreign geometry rendered
outside that interface or a provider replacing/bypassing the visitor callbacks.
Real third-party DLL/game combinations still require in-game verification.

## Confirmed defect: insufficient branch-read window

The decoder recognizes ENDBR64 followed by `mov r11, imm64; jmp r11`, which is
17 bytes, while the production resolver read only 16. The existing decoder
unit test supplied 20 bytes directly and therefore missed the production
failure. A fixed-size 16-byte memory probe also rejected a complete short
veneer immediately before an unreadable page.

Fix: read up to 20 executable/readable bytes, stopping at the accessible
prefix, and let the decoder validate the required instruction length. Cycle
and depth limits remain. Exact engine-target resolution checks an address,
not membership in the executable module as a whole.

### Conservative-guard follow-up review

Reviewed added early exits in the 1.5.7 -> 1.6.0 source diff, plus current
RaceMenu, DAVE, Virtual Token/DD initialization and runtime-layout gates.
No additional unknown-provider gate that disables the complete registered-
attachment pass was found in that scope. Distinguish this from full parity:

- RaceMenu previously treated a partial map as completed initialization. Fixed:
  retry missing interfaces/hooks at DataLoaded and its queued post-broadcast
  fence; retain working connections after a later failed exchange. BodyMorph,
  transforms and attachment observer remain independently negotiated.
- RaceMenu now uses the last compatible public prefix for higher interface
  versions instead of rejecting an unfamiliar number. Readable/executable
  memory checks remain; they are not semantic ABI proof. Higher versions log
  the assumption. The exact two version-zero attachment layouts remain
  distinguished. See `RaceMenu-Version-Compatibility-v1.6.1.md` for all 19
  source-change snapshots, current routing and package-to-binary evidence gaps.
- DAVE early messaging failure previously latched API unavailability and the
  PostPostLoad decision immediately installed native hooks. Fixed: preserve
  retries, postpone an ambiguous decision until after every DataLoaded handler,
  and force one final query past the throttle. Normal DAVE ownership remains
  unchanged. Only after this final rendezvous does API absence select working
  DAV/native fallback; do not switch owners after native hooks are installed.
- A failed DAVE RefreshActor previously skipped all subsequent restoration.
  Fixed: rebuild that actor through the existing engine hooks and run the same
  pose/dye/heel follow-ups. This is not a mid-game native-hook takeover.
- Late registered attachments now re-arm saved dye restoration independently
  of BodyMorph availability, repairing the gap after bounded early retries
  expire. No morph ownership, shader/material originals or save schema changes.
- Grid Costume previously rejected any ABI number or structure size other
  than exactly v1/24 bytes. Fixed: consume the existing message/ItemKey prefix
  with valid length/count bounds and log unfamiliar ABI assumptions. Future
  changes to ItemKey stride/semantics remain a compatibility risk, not verified
  merely by the message size. Restored/empty/non-player states retain their
  existing intentional behavior; these are not version gates.
- OAR registration previously used call_once even on API failure. Fixed:
  retry missing/failed conditions at later startup fences and latch success
  per condition. Successful conditions are not registered twice.
- Virtual Token records and selective Papyrus hooks are validated before
  interception; DD script-property reads fail locally when unavailable, and
  DD settings are queried again after load. Ordinary appearance attachment is
  independent. Missing required helper records still prevent token operation.
- Unknown game layouts and invalid custom-skin instruction/resume layouts
  remain rejected. These guards prevent unverified offsets/continuations;
  they are not evidence of a defect and were not weakened for compatibility.
- Kit scan-state guards protect in-progress results, and condition/drop
  validation rejects stale/invalid operations without partially committing.

## Reproduction and validation

`CustomSkinningRegressionTests` compiles verbatim production functions extracted
by `Generate-CustomSkinningTestSource.ps1`: both hook installers and their Xbyak
stubs, visitor dispatch, memory validation and trampoline resolution. The test
executes the generated x64 stubs with recording fake engine/provider objects.

- Before the attachment fix, it failed with: `an unknown pre-patched CALL must
  not disable registered wig/clothing attachment`.
- After that fix, adding the 17-byte production veneer case failed the verified
  filtering assertion; correcting the read window made it pass.
- Disabling only the new production callback scope reproduced
  `opaque provider must filter hidden actual equipment without replacing the concrete visitor`;
  restoring the scope made the same integration test pass.
- 40 cases cover both SE and AE register paths, active/inactive SFS,
  hidden/visible actual equipment, direct engine, direct IED, opaque foreign
  CALL, IED veneer and exact-engine veneer. Check one attachment, actor and
  weight-model argument identity, original foreign visitor identity, filtered
  engine dispatch, and deferred IED calls.
- Opaque cases execute the actual production callback filter through real
  virtual calls and verify hidden/visible callback results for all three slots.
  Additional cases verify rejected-write safety, idempotent install, unchanged
  vptr/RTTI/destructor/concrete data, null and non-armor forwarding, return/output
  preservation, unrelated visitors, cross-thread isolation, nested same/different
  visitors, inactive shadow scopes, and exception restoration.
- Guarded allocation cases cover complete page-end veneers, cycles, truncated
  branches and null addresses. Invalid CALL-site opcodes remain unpatched.

The full fast suite additionally checks BodyMorph ownership and production
tracking, RaceMenu ABI, runtime layouts, condition/drop logic, kit/body filters,
dye rules, strip policies, save lifecycle and compatibility package contracts.
No real game, reporter save, NIF renderer, DAVE/DAV plugin, or IED DLL is
executed by the new harness. Reporter-specific resolution remains unverified.
