# SkyUI 간접 조회 비용을 줄이는 대체 설계

상태: 1단계 구현·회귀 검사 완료. 2단계는 최신성 경계 미검증으로 미적용.
제품 코드와 로컬 DLL만 갱신했으며 MO2/배포 ZIP/GitHub는 변경하지 않았다.
근거: [확대 점검 결과](SKYUI-PERFORMANCE-COVERAGE-2026-09-29.md).
구현·검증: [1단계 수정 기록](SKYUI-QUERY-COST-FIX-2026-09-29.md).

## 목표

SkyUI의 아이템별 능력치/조건 조회에 SFS의 전체 외형 재계산 비용이 반복해서
붙지 않게 한다. 누드 판정, 실제 장비 숨김, 등록 외형, 조건, 모든 탈의연동,
OAR/IED/Wet/Footprints의 의미와 DAVE/DAV/native 동작을 유지한다.
게임/SkyUI/다른 모드 자체의 소요 시간까지 0으로 만들겠다는 목표는 아니다.

권장 순서는 무상태 중복 제거 → 기존 표시 결정의 내부 읽기 경로 재사용이다.
별도 누드 판정 엔진, 별도 실제 장비 관리, SkyUI SWF/SKSE DLL 패치는 만들지 않는다.

## 1단계 — 조회 의미를 바꾸지 않는 개선

### 요청 하나 안에서 착용 수집을 공유

기존 EquippedArmorSnapshot을 GetHiddenRealEquipmentSlotMask/CollectHiddenWornSlotMask에도
전달한다. 최종 표시 질의와 같은 방식으로 한 요청의 BuildDisplaySet과 숨김 슬롯
계산이 같은 수집 결과를 사용한다. 요청이 끝나면 파기하므로 이후 장착/해제/탈의가
이전 결과에 가려질 수 없다. 관련 스키닝 호출의 동일한 중복도 개별 확인 후 적용한다.

기대되는 검증 가능한 변화: 숨김 슬롯 질의 1,000회에 수집 2,000회 → 1,000회.
이 단계만으로 질의 간 반복이나 제보자의 4초가 사라진다고 주장하지 않는다.

후속 구현에서는 최종 외형/몸통 질의도 같은 BuildDisplaySet이 이미 계산한
보이는 실제 장비 목록을 요청 내에서 이동 전달한다. 공개 API 캐시 읽기나
질의 간 재사용이 아니며, 출력이 없는 경로는 기존 직접 계산을 유지한다.

### 실행용 조건 접근 경량화

동일 MaterializationState에서 실행용 shared_ptr<TESCondition>만 얻는 접근을 제공한다.
기존 UI용 MaterializedCondition은 유지한다. 실행 경로가 사용하지 않는 signature,
displayCnf, refreshTargets 복사를 없앤다. 조건을 재작성하거나 평가 횟수를 임의로
합치지 않는다. 엔진 문자열 저장소 수명과 편집/삭제/로드 중 소유권을 유지한다.
캐시 무효화, 실패 후 재시도도 기존 경로를 공유한다.

### 타입 검사 캐시 충돌 완화는 별도 변경

128칸 direct-mapped의 충돌 퇴출을 작은 set-associative/LRU 등 제한된 소유권
구조와 비교한다. 무제한 타입 보관이나 클래스 이름 기반 영구 완료 처리는 금지한다.
최초 즉시 패치, post-link 장벽, 늦은 native 등록 revision, P+ member 재시도는 유지한다.
캐시 hit 최적화이며 외부 모드 감시 범위를 줄이는 작업이 아니다.

## 2단계 — 표시 결정은 갱신에서, 질의는 읽기로

현재 BuildDisplaySet은 조건/숨김/탈의/특수 슬롯/호환 결정을 계산하고,
PrepareOutfitValue는 보이는 실제 장비·등록 외형·몸통 플래그를 이미 구성한다.
WornHasKeyword/OAR/발자국/숨김 조회가 이와 같은 결정을 각각 다시 만드는 대신,
같은 계산에서 나온 불변 내부 읽기 자료를 재사용하는 방안을 채택한다.

### 기존 외부 API의 AcquirePublished를 바로 연결하지 않는다

현재 공개 경로는 task pump와 최대 64개 publication batch를 거친다.
dirty/NotReady인 actor는 AcquirePublished가 빈 결과를 돌려준다.
이를 바로 WornHasKeyword에 연결하면 변경 직후 바닐라 판정으로 튀거나
아직 준비되지 않은 값을 '나체'로 취급할 수 있다.

따라서 내부 읽기 자료와 외부 알림 대기는 구분하되, **표시 계산 원천은 하나**로 유지한다.
기존 provider/결정 경로에 내부 접근을 추가하는 것이며 외부 ABI 변경은 필수 조건이 아니다.
별개로 또 계산하는 두 번째 캐시는 만들지 않는다.

### 내부 자료의 범위

- 실제 표시 대상과 등록 외형의 FormID, 실제/등록 구분, 표시 슬롯.
- 같은 착용 스냅샷에서 산출한 hidden-actual / visible-additional 슬롯 마스크.
- actor의 표시 관리 여부 및 결정 revision, load epoch, 3D/장면 세대.
- engine actor/node 포인터를 소유하거나 수명 밖에서 재사용하지 않는다.

기존 공개 Value는 보이는 아이템만 저장하므로 그것만으로 숨긴 실제 장비 마스크를
역산하면 안 된다. 숨김 마스크는 현재 ShouldHideRealArmor의 판정으로 함께 산출한다.
기존 active 판단에는 SOS/TNG 보정과 force-visible 상태도 포함된다. 작업대 행이
없다는 이유만으로 플레이어를 무조건 NotManaged 처리하지 않는다.

### 질의별 읽기

- WornHasKeyword: 기존 두 몸통 키워드와 재진입 가드를 유지한다.
  표시 목록으로 기존 SnapshotHasBodyKeyword 의미를 적용한다.
- OAR: 표시 대상 목록에 현재의 predicate/keyword 판단만 한다.
- Wet/숨김 질의: 준비된 숨김 마스크·등록 표시 마스크를 읽는다.
- Footprints: 동일 표시 자료에서 기존 등록 신발 우선/맨발 구분을 유지한다.
- IED: 기존 published-view/actor reevaluation 계약을 보존한다.

키워드 결과를 영구 고정하지 않는다. 다른 모드가 표시 장비의 키워드를 직접
바꿀 수 있으므로, 표시 목록을 재사용하더라도 필요한 키워드/관련 속성은 그 소수의
장비에서 현재 값을 확인하는 선택지가 더 안전하다. 이는 전체 인벤토리 수집이나
조건 재실행과 다르다. 이 경우 hot query 목표는 O(표시 장비 수)이며 무조건 O(1)이라고
표현하지 않는다. 적절한 변경 통지가 검증된 필드만 플래그로 바로 읽는다.

## 반드시 먼저 해결할 최신성 경계

현재 NotifyRefresh는 refresh가 실제 실행되는 시점에 호출되고, NotifySkinning은
visitor 시작 시점에 기록된다. **후자는 attachment 완료나 GPU 렌더 완료 신호가 아니다.**
어느 것도 그대로 '최종 완료' 플래그로 사용해서는 안 된다.

| 변경 경계 | 필요한 확인/동작 |
| --- | --- |
| 실제 장착·해제, 외부 장비 변경 | 관련 actor의 이전 결정 재사용 금지 시점을 mutation/event에서 확보. item 목록 열기 자체를 변경으로 보지 않음. |
| 등록/삭제/키트/전역·개별 숨김/미리보기 취소 | 기존 workbench revision과 actor refresh 요청을 연결. 큐가 나중에 실행돼도 변경 세대가 이미 구분돼야 함. |
| 모드설정·바닐라 슬롯·직접편집 두 경로 | 각 suppression/restore 변경을 같은 actor 결정 세대에 연결. 실제 장비를 대신 입히지 않음. |
| SL 재착의 off, P+, DD | 이벤트 종료와 실제 재착의를 혼동하지 않음. 유지해야 할 숨김과 사용자의 수동 표시 제어를 각각 기존대로 보존. |
| 조건 참·거짓, 날씨/시간/위치 등 | 기존 이벤트 및 500ms 폴링 유지. SkyUI가 열렸다는 이유로 조건 판정을 끄거나 주기를 늘리지 않음. |
| 확률·자기참조 몸통 조건 | query마다 가상으로 다른 외형을 재결정하는 것과 렌더에 사용한 결정을 읽는 의미 차이를 명시적으로 검증. 재진입 시 기존 원본 답 가드 유지. |
| HT2·SOS/TNG·분류/설정 변경 | 표시 슬롯/몸통 결과 영향까지 무효화. 모프/HH/염색의 리소스 소유권은 바꾸지 않음. |
| DAVE / DAV / native | 교체·지연 부착·변하지 않은 attachment 유지 모두 확인. DAVE callback이 항상 온다고 가정하지 않음. |
| unload/delete/3D 교체/load/revert | 기존 lifecycle에 맞춰 폐기. 이전 actor/scene의 ready 결과를 되살리지 않음. |

자료가 없거나 현재 변경 세대의 유효성이 확인되지 않으면, 기능을 막거나
false/나체로 고정하지 않고 기존 정확 계산을 fallback으로 유지한다.
다만 이 fallback이 모든 메뉴 항목에서 반복되면 성능 목표를 못 달성하므로
같은 안정 상태를 준비 완료로 만드는 경로와 중복 생성 합치기를 함께 검증해야 한다.
렌더 완료와 계산 완료를 혼동한 상태에서 캐시 hit를 늘리는 것은 허용하지 않는다.

변경 중 어느 시점의 상태를 읽을지도 회귀 기준으로 고정해야 한다. 단순히
'이전 published 값이면 충분하다'고 바꾸지 않고, 기존 즉시 조회와 실제 렌더 결정이
어긋나는 사례를 비교한다. 특히 first query, preview, empty-equipment DAVE bootstrap,
조건에 의한 표시 변경은 2단계의 통과 조건이다.

## 성능/동작 통과 기준

1. 무변경 상태에서 100/1,000/10,000개의 목록 관련 몸통 질의를 해도 SFS의 추가
   VisitWornItems/조건 materialization/IsTrue/refresh 예약이 질의 수만큼 늘지 않는다.
   실제 게임에서 호출되는 원본 함수 비용은 따로 측정한다.
2. 변경 1회는 해당 actor만 갱신한다. 다른 액터 스캔, 메뉴 전체/세계 재평가는 없다.
3. 위 변경 경계를 낀 연속 질의가 현재처럼 적절한 값을 내며 오래된 장비/몸통
   결과를 반환하지 않는다. '첫 조회 false, 나중에 정상'은 성공이 아니다.
4. 소유권은 actor lifecycle에 묶이고 unload/delete/load/reset 후 잔류하지 않는다.
5. 동일 조건의 평가 횟수/결과 의미, 실제 장비 제어 권한, 문자열 및 노드 수명을
   성능 개선을 이유로 바꾸지 않는다. 필요해지는 의미 변화는 구현 전에 명시한다.
6. 본체에 상시 상세 로그/호출별 타이머를 남기지 않는다. 분리 검사와 제한된 계측을 사용한다.

## 채택하지 않을 대안

- 인벤토리/대화 중 WornHasKeyword 보정을 끄기.
- 0.5초/수초짜리 무조건 TTL 또는 frame ID만으로 상태가 같다고 간주하기.
- 엔진/RE 객체를 임의 worker에서 읽어 재계산을 백그라운드로 옮기기.
- 공개 API NotReady를 누드/미관리로 치환하기.
- 특정 RaceMenu/DAVE/외부 모드 이름을 성능상 이유로 배제하기.
- 확인되지 않은 engine/SKSE 주소나 별도 SkyUI 후킹으로 메뉴 경로부터 갈아엎기.

실행 순서는 1단계의 좁은 개선부터 검증하고, 2단계 최신성 경계가 확인된 뒤 공통
읽기 경로를 적용하는 것이다. 2단계의 장면 준비 문제는 현재 아직 구현/실행 검증하지 않았다.
